## 1. Анализ и требования

**Предметная область.** Справочные материалы КГЭУ (инструкции, порядки действий, ответы на частые вопросы) разбросаны по сайту, ЭИОС, чатам и подразделениям. Автор материала отправляет текст по почте, не знает, взялся ли кто-то за него, а студенты находят противоречивые версии и повторно звонят в подразделения.

**Что автоматизируется.** Согласование материала перед публикацией: заявка проходит путь «Поступила → На проверке → Опубликовано / Отклонено», и в любой момент видно, кто отвечает за материал.

**Роли и границы.** Автор подаёт заявку, координатор назначает редактора, редактор проверяет и публикует. В семестр входят согласование и три экрана; ИИ-помощник по опубликованным материалам вынесен в запас ВКР.

**Три критерия приёмки** (дано / когда / тогда) — в [`lab-01-requirements.md`](lab-01-requirements.md), прогон — в [`acceptance-check.md`](acceptance-check.md).

**Артефакты:** [`project-proposal.md`](project-proposal.md), [`lab-01-requirements.md`](lab-01-requirements.md).

## 2. Проектирование и архитектура

**Три узла.** React + Vite (`:5173`) → ASP.NET Core (`:5000`) → PostgreSQL (`:5432`). Это архитектура web-ИС семестра. Прямой стрелки от браузера к базе нет: иначе клиент получил бы пароль от базы и обошёл серверные правила.

**Данные.** Справочник подразделений, пользователи, главный объект — заявка на публикацию. Название подразделения хранится один раз в `departments`, в заявке лежит `department_id` (3НФ). У новой заявки `assignee_user_id` равен NULL. Статус ограничен четырьмя значениями через `CHECK`.

**Процесс.** Назначение редактора и смена статуса — разные действия с разными правами и разными запросами.

**Артефакты:** [`architecture.md`](architecture.md), [`data-model.md`](data-model.md), [`api-contract.md`](api-contract.md), [`requirements-matrix.md`](requirements-matrix.md).

## 3. Клиентская часть

**Стек.** React 19 + Vite, JavaScript, react-router-dom (клиент на React согласован с преподавателем 06.10.2026; сервер и база — стек курса).

**Экраны.** `/` — список заявок с действиями по роли, `/new` — создание, `/login` — вход. Шапка одна, снаружи маршрутов.

**Состояния списка.** loading / empty / data / error — одно значение состояния, взаимоисключающий вывод.

**Проверка полей на клиенте.** Заголовок 5–80 после `trim`, `departmentId` — целое больше нуля, описание 10–500. Серверная проверка повторяет те же правила.

**Семантика и безопасность вывода.** `main`, `form`, `label`, `table`; описание выводится подстановкой React, поэтому `<script>alert(1)</script>` отображается текстом.

**Артефакты:** `frontend/src/`, отчёты [`reports/lab-03.md`](reports/) … `lab-06.md`.

## 4. Сервер и программный интерфейс

**Слои.** Контроллер принимает HTTP, сервис хранит правила процесса, хранилище скрыто за интерфейсом `IPublicationRequestStore` (список в памяти в ЛР8, PostgreSQL через EF Core с ЛР10). Зависимости приходят через DI.

**Маршруты.**

| Метод и путь | Успех | Отказы |
|---|---|---|
| `POST /api/publication-requests` | 201 | 400, 401, 403 |
| `GET /api/publication-requests` | 200 (включая `[]`) | 401 |
| `GET /api/publication-requests/{id}` | 200 | 401, 404 |
| `PATCH /api/publication-requests/{id}/assignee` | 200 | 400, 401, 403, 404, 409 |
| `PATCH /api/publication-requests/{id}/status` | 200 | 400, 401, 403, 404, 409 |

`DELETE` не используется: отмена — это статус `Cancelled`.

**Разделение 400 и 409.** 400 — данные не прошли проверку (короткий заголовок, неизвестный статус, несуществующее подразделение). 409 — данные корректны, но действие противоречит состоянию процесса (перевод в работу без назначенного редактора, переход `Closed → New`).

**Безопасный сбой.** Неожиданное исключение пишет в лог одну строку вида `POST /api/publication-requests failed; error=InvalidOperationException`, а клиент получает `{"error":"server_error","message":"Сервер не смог обработать запрос"}` без stack trace.

**Артефакты:** `backend/`, [`api-collection/`](api-collection/), отчёты `lab-07.md`, `lab-08.md`.

## 5. База данных

**Схема.** `departments`, `users`, `publication_requests` с PK, FK, `CHECK` на статусы и роли, индексами по статусу, подразделению и назначенному редактору. Имена в `snake_case`, модель EF Core сопоставлена с ними явно.

**Запросы.** Фильтр с сортировкой, `JOIN` со справочником, `GROUP BY` по статусам и по подразделениям — [`../db/queries.sql`](../db/queries.sql).

**Миграции.** Схему создаёт `dotnet ef database update`; каталог `backend/Migrations` хранится в Git. Строка подключения лежит в user-secrets, в репозитории её нет.

**Артефакты:** [`../db/schema.sql`](../db/schema.sql), [`../db/seed.sql`](../db/seed.sql), отчёты `lab-09.md`, `lab-10.md`.

## 6. Вход и права

Вход — cookie-сессия (`kb.session`, HttpOnly, SameSite=None, Secure), пароли хранятся как хэш `PasswordHasher<User>` из ASP.NET Core Identity. Гость получает 401, вошедший без нужной роли — 403, редактор не двигает чужую заявку — 403. Полная таблица прав — [`role-matrix.md`](role-matrix.md).
