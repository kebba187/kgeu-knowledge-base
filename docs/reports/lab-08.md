## 1. Цель

Сервер отвечает на маршруты заявки: список, одна запись, создание, отдельно назначение редактора, отдельно смена статуса. Коды предсказуемы: `201`, `200`, `400`, `404`, `409`. Неожиданный сбой пишется в лог, а клиент получает безопасное сообщение.

## 2. Что сделали

1. `Dtos/CreatePublicationRequest.cs` — клиент присылает только `title`, `departmentId`, `description`; `id`, `number`, `status` и редактора задаёт сервер.
2. `Dtos/AssignEditorRequest.cs` и `Dtos/ChangeStatusRequest.cs` — два разных тела для двух разных действий.
3. `Dtos/PublicationRequestResponse.cs` — формат ответа из `docs/api-contract.md`.
4. `Services/PublicationRequestService.cs` — правила процесса: номер вида `БЗ-2026-0001`, статус `New` при создании, запрет перехода в `InProgress` без назначенного редактора, таблица допустимых переходов.
5. `Controllers/PublicationRequestsController.cs` — пять маршрутов, перевод результата сервиса в коды ответа.
6. `Dtos/ApiError.cs` — единый формат отказа; ошибки проверки полей возвращаются через `InvalidModelStateResponseFactory`.
7. Обработчик неожиданных ошибок в `Program.cs`: одна строка в лог, безопасный ответ клиенту.
8. Коллекция запросов: `docs/api-collection/publication-requests.postman_collection.json`.

## 3. Доказательство успеха

Проверено на запущенном сервере (`http://localhost:5000`):

| № | Запрос | Ожидание | Факт |
|---|---|---|---|
| 1 | `POST /api/publication-requests` с корректными полями | 201, `id`, `number`, `status: New` | `201`, `{"id":1,"number":"БЗ-2026-0001","status":"New","assigneeUserId":null}` |
| 2 | `GET /api/publication-requests` | 200, массив | `200`, 1 запись |
| 3 | `PATCH /{id}/assignee` `{"assigneeUserId":3}` | 200, статус не меняется | `200`, `assigneeUserId=3`, `status=New` |
| 4 | `PATCH /{id}/status` `{"status":"InProgress"}` | 200 | `200`, `status=InProgress` |

## 4. Доказательство отказа

| Что сделали | Ожидание | Факт |
|---|---|---|
| `POST` с `title` = `abc` | 400 | `400 {"error":"validation","fields":{"title":"От 5 до 80 символов"}}` |
| `GET /api/publication-requests/999999` | 404 | `404 {"error":"not_found","message":"Заявка 999999 не найдена"}` |
| `PATCH /{id}/status` до назначения редактора | 409 | `409 {"error":"conflict","message":"Сначала назначьте редактора…"}` |
| `PATCH /{id}/status` `{"status":"New"}` из `InProgress` | 409 | `409 «Нельзя перевести заявку из InProgress в New»` |
| `PATCH /{id}/status` `{"status":"Done"}` | 400 | `400`, поле `status` |
| `DELETE /api/publication-requests/{id}` | маршрута нет | `405 Method Not Allowed` |

## 5. Лог неожиданной ошибки

Во время проверки в `PublicationRequestService.Create` временно добавлена строка:

```csharp
if (request.Title.StartsWith("СБОЙ")) throw new InvalidOperationException("учебный сбой");
```

Результат:

```text
fail: UnhandledException[0]
      POST /api/publication-requests failed; error=InvalidOperationException; message=учебный сбой
```

Клиент получил `500` и тело `{"error":"server_error","message":"Сервер не смог обработать запрос"}` — без stack trace, путей и тела запроса. Искусственный сбой убран до коммита.

## 8. Ответы к защите

1. **Почему назначение и статус — два PATCH?** Это разные действия разных ролей с разными правилами. Раздельные маршруты позволяют назначить редактора, не трогая статус, и проверять права отдельно.
2. **Чем 400 отличается от 409?** 400 — присланные данные не прошли проверку (короткий заголовок, неизвестный статус). 409 — данные корректны, но действие противоречит состоянию процесса (перевод в работу без редактора).
3. **Почему пустой список — 200, а не 404?** Коллекция существует, просто сейчас она пуста. 404 означал бы, что самого маршрута или ресурса нет, и клиенту пришлось бы различать «нет данных» и «нет адреса».
4. **Что видит клиент и разработчик при неожиданном сбое?** Клиент — короткое сообщение и код 500. Разработчик — одну строку лога с методом, путём и типом исключения, без тела запроса и секретов.
