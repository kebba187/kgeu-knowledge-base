## 1. Цель

Разобрать единственный файл `App.jsx` на страницы и переиспользуемые компоненты и научить приложение переключать экраны по адресу в строке браузера без перезагрузки страницы.

## 2. Что сделали

1. Подключён `react-router-dom`; маршруты описаны в `src/router.jsx`.
2. Заведены три страницы: `pages/TicketList.jsx` (`/`), `pages/TicketNew.jsx` (`/new`), `pages/Login.jsx` (`/login`).
3. Выделены компоненты: `components/AppHeader.jsx` — шапка с названием и ссылками, `components/TicketTable.jsx` — таблица заявок.
4. `App.jsx` сократился со 189 строк до оболочки: шапка плюс место, куда маршрутизатор подставляет текущую страницу.
5. Заведено хранилище списка `src/ticketsStore.js` — массив заявок вынесен из компонента в отдельный модуль.
6. Заведён `src/dictionaries.js`: подписи статусов для экрана (`New` → «Поступила») и учебный справочник подразделений.
7. `TicketTable` получает данные только через `props` и не хранит своей копии массива.
8. Стили перенесены из общего файла под новую структуру.

> Таблица ничего не знает о том, откуда взялись заявки: её можно показать и с данными из памяти, и с данными с сервера. Это и есть смысл разделения на компоненты.

## 7. Ответы к защите

1. **Чем страница отличается от компонента?** Страница соответствует адресу и собирается маршрутизатором; компонент — переиспользуемая часть, которую можно вставить на любую страницу. `TicketTable` — компонент, `TicketList` — страница.
2. **Почему переход по ссылке не перезагружает страницу?** Маршрутизатор перехватывает нажатие, меняет адрес средствами браузера и подставляет другой компонент. Запроса к серверу за новым HTML не происходит — это и означает «одностраничное приложение».
3. **Почему таблица не хранит свой массив?** Если бы хранила, на экране оказались бы две копии данных, и они разошлись бы после первого же изменения. Данные живут в одном месте, таблица получает их через `props`.
4. **Зачем отдельный `dictionaries.js`?** Коды статусов приходят с сервера на английском, а на экране нужны русские подписи. Перевод — дело интерфейса, поэтому он лежит на клиенте, а не в API.
