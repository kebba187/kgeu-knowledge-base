## 1. Цель

Перевести требования ЛР1 в проект: из каких узлов состоит система, какие таблицы хранят данные и какими запросами клиент общается с сервером. Кода по-прежнему нет — только документы, по которым код будет написан.

## 2. Что сделали

1. Написан [`docs/architecture.md`](architecture.md): три узла — клиент в браузере, сервер приложений, система управления базами данных; адреса `5173`, `5000`, `5432`; кто за что отвечает.
2. Обосновано, почему браузер не обращается к базе напрямую: иначе клиенту пришлось бы передать пароль базы, а серверные правила можно было бы обойти.
3. Написан [`docs/data-model.md`](data-model.md): три таблицы — `departments`, `users`, `publication_requests` — с типами, ключами и ограничениями.
4. Схема приведена к третьей нормальной форме: название подразделения хранится один раз в `departments`, в заявке лежит только `department_id`.
5. Зафиксировано правило имён: `camelCase` в JSON, `PascalCase` в C#, `snake_case` в базе.
6. Написан [`docs/requirements-matrix.md`](requirements-matrix.md): каждое ФТ из ЛР1 связано с полем модели, запросом API и ожидаемым кодом ответа.
7. Написан [`docs/api-contract.md`](api-contract.md): таблица адресов, четыре статуса, таблица допустимых переходов, коды ответов и примеры JSON.
8. Приняты два решения, которые действуют весь семестр: назначение редактора и смена статуса — **разные** запросы `PATCH`; метода `DELETE` нет, отмена — это статус `Cancelled`.

> `api-contract.md` добавлен по замечанию ревью (issue #1): в первом варианте ЛР2 контракта не было, и матрица требований ссылалась на несуществующий документ.

## 7. Ответы к защите

1. **Почему браузер не пишет в PostgreSQL напрямую?** Клиент получил бы пароль базы, и любой пользователь смог бы обойти серверные правила: переходы статусов, проверку ролей и длины полей. Сервер существует именно для того, чтобы правила нельзя было обойти.
2. **Почему название подразделения не хранится в каждой заявке?** Переименование «Учебного отдела» потребовало бы править сотни строк, а пропустив одну, получили бы два названия для одного подразделения. Хранится один раз, ссылка по `id` — это третья нормальная форма.
3. **Чем `id` отличается от `number`?** `id` — машинный ключ для базы и адресов API. `number` вида `БЗ-2026-0001` — номер для людей: его называют по телефону и пишут в письмах.
4. **Почему назначение и смена статуса — разные `PATCH`?** Это действия разных ролей: назначает координатор, статус меняет редактор. Разделив запросы, права можно проверять по отдельности; с одним общим запросом пришлось бы разбирать тело, чтобы понять, что именно пытаются изменить.
