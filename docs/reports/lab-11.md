## 1. Цель

Гость не создаёт заявки, редактор не двигает чужие, назначение и смена статуса — разные права. Пароли хранятся хэшем, опасный HTML в описании выводится текстом.

## 2. Выбор механизма входа

Выбран вход по **cookie-сессии** (не JWT):

- cookie `kb.session` помечена `HttpOnly`, поэтому JavaScript её не читает и токен нельзя украсть через XSS;
- клиент на `:5173` и API на `:5000` — разные источники, поэтому cookie настроена как `SameSite=None; Secure`, а CORS разрешает только `http://localhost:5173` с `AllowCredentials`;
- запросы с клиента идут с `credentials: "include"`.

## 3. Что сделали

1. `backend/Auth/AuthController.cs` — `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`.
2. Пароли: `PasswordHasher<User>` из ASP.NET Core Identity (соль и стоимость внутри библиотеки).
3. `backend/Data/DatabaseSeeder.cs` — три учебные учётки с хэшами создаются при старте в Development.
4. Контроллер заявок закрыт `[Authorize]`; создание — роль `Author`, назначение — `Coordinator`, смена статуса — `Editor`.
5. Проверка владельца: `PublicationRequestService.ChangeStatus` сравнивает `AssigneeUserId` с id из claims и возвращает 403 для чужой заявки.
6. `backend/Auth/UsersController.cs` — список редакторов для координатора.
7. Клиент: `src/api/auth.js`, `src/authStore.js`, экран `/login`, имя и роль в шапке, кнопка «Выйти».
8. Матрица ролей: `docs/role-matrix.md`.

## 4. Доказательство успеха

| Проверка | Как | Результат |
|---|---|---|
| вход автором | форма `/login`, `author` / `Author-2026` | `POST /api/auth/login` → `200`, в шапке «Сотрудник учебного отдела · автор» |
| сессия переживает F5 | обновить страницу | `GET /api/auth/me` → `200`, пользователь тот же |
| cookie защищена | DevTools → Application → Cookies | `kb.session`, `HttpOnly = true`, `Secure = true`, `SameSite = None` |
| выход | кнопка «Выйти» | `POST /api/auth/logout` → `204`, затем `GET /api/auth/me` → `401` |

## 5. Доказательство отказов

| Проверка | Ожидание | Факт |
|---|---|---|
| `POST` заявки без входа | 401 | `401 {"error":"unauthorized","message":"Нужно войти в систему"}` |
| неверный пароль | 401 | `401 {"error":"unauthorized","message":"Неверный логин или пароль"}` |
| автор назначает редактора | 403 | `403 {"error":"forbidden","message":"Недостаточно прав для этого действия"}` |
| координатор меняет статус | 403 | `403` |
| редактор двигает чужую заявку | 403 | `403 «Статус меняет только редактор, назначенный на эту заявку»` |
| назначенный редактор меняет статус | успех | `200`, статус `InProgress` |

## 6. Пароли в базе

```sql
SELECT login, role, left(password_hash, 16) AS hash_start, length(password_hash) AS hash_length
FROM users;
```

Ожидание: строка вида `AQAAAAIAAYagAAAA…` длиной около 84 символов, не равная паролю и не раскодируемая из Base64 в читаемый текст.

Вставить скрин результата.

## 7. Проверка опасного HTML

Создана заявка с описанием `<script>alert(1)</script> текст должен быть виден как есть`.

| Ожидание | Факт |
|---|---|
| символы `<script>…` видны в списке | да, описание выводится текстом |
| окно `alert` не появляется | не появилось |

React подставляет значение через `{item.description}` и экранирует его; `dangerouslySetInnerHTML` в проекте не используется — это аналог запрета `v-html`.
